# YOLO Trainer Platform

[![CI](https://github.com/quick-1y/yolo-trainer/actions/workflows/ci.yml/badge.svg)](https://github.com/quick-1y/yolo-trainer/actions/workflows/ci.yml)

[English version](README.md)

## Что это такое

YOLO Trainer Platform — это самостоятельно размещаемый (self-hosted) веб-сервис в Docker для разметки наборов изображений и обучения моделей [Ultralytics YOLO](https://docs.ultralytics.com/) на них — локальная замена рабочего процесса аннотации и обучения в стиле Roboflow. Фаза 1 (этот релиз) реализует работающий каркас: веб-интерфейс в браузере на базе сервиса FastAPI, контейнер-воркер и постоянное управление проектами (создание, список, переименование, удаление проектов `detect`/`segment`). Загрузка изображений, аннотация и обучение появятся в следующих фазах — полный план смотрите в [`.planning/ROADMAP.md`](.planning/ROADMAP.md).

## Уведомление о безопасности — прочитайте перед запуском

**В версии v1 у этого сервиса нет аутентификации.** Любой, кто может достучаться до его адреса по сети, получает полный, неограниченный доступ — без входа в систему, без API-ключей.

- По умолчанию сервис слушает только `127.0.0.1` (только этот компьютер). Это безопасно.
- Установка `BIND_ADDR=0.0.0.0` (или любого адреса, отличного от loopback) в `.env` открывает сервис **для всех в вашей локальной сети**. Делайте это только если вы понимаете и принимаете этот риск, и добавьте адрес/имя хоста вашей локальной сети в `ALLOWED_HOSTS` (см. [Конфигурацию](#конфигурация)), иначе запросы будут отклонены.
- Файлы моделей `.pt` — это файлы Python pickle, и они **могут выполнять произвольный код при загрузке**. Загружайте `.pt` файлы только из источников, которым вы доверяете.

## Быстрый старт с Docker

Требования:
- **Windows/macOS:** Docker Desktop
- **Linux:** Docker Engine + Compose v2
- Достаточно машины только с CPU — GPU не требуется.

Шаги:
```bash
# опционально: скопируйте пример файла окружения и настройте его
cp .env.example .env

docker compose up --build
```
Первая сборка скачивает CPU-версию PyTorch и Ultralytics, что занимает несколько минут. После запуска откройте **http://127.0.0.1:8080**.

Остановить стек:
```bash
docker compose down
```
Обновить до новой версии:
```bash
git pull
docker compose up --build
```
Образы собираются локально из исходного кода — в v1 нет ни реестра, ни готовых образов.

## Ваши данные

Всё, что хранит приложение (сегодня — база данных SQLite; в следующих фазах — изображения, модели и результаты обучения), находится в `./data` рядом с `docker-compose.yml`, либо в каталоге, указанном переменной `DATA_DIR` в `.env`. Эта папка:
- **Сохраняется** между `docker compose down` / `up` и пересборками образов.
- Автоматически получает применённые миграции базы данных при каждом запуске контейнера `api`.
- Может быть **сохранена в резервную копию** — остановите стек (`docker compose down`) и скопируйте папку.
- В Linux файлы внутри принадлежат `root`, так как контейнеры работают от root.
- Хранит загруженные изображения в `data/projects/<project id>/images/`, а миниатюры — в `data/projects/<project id>/thumbs/`. Оригиналы сохраняются точно в том виде, в котором были загружены.
- Хранит каждый запуск обучения в `data/runs/<run id>/`: снимок набора данных (изображения как жёсткие ссылки, разметка, `data.yaml`, `manifest.json`), файлы прогресса и журнала, а также веса запуска.
- Хранит каждую модель, которую можно скачать, в `data/models/<model id>.pt`.
- Хранит скачанные сервисом официальные базовые веса (например, `yolo26n.pt`) в `data/weights/`.
- Удаляет запуски и модели проекта вместе с самим проектом.
- **Не имеет дисковой квоты**: загрузка множества больших изображений может заполнить диск, поэтому следите за свободным местом.

## Разметка изображений

Откройте изображение, нажав на его плитку на странице **Images** проекта; сортировка и поиск сетки сохраняются, поэтому стрелки «предыдущее / следующее» в редакторе перемещаются по тому же списку. Кнопка **Annotate next** в проекте открывает следующее изображение, у которого ещё нет разметки.

- **Рисуйте рамки** инструментом «Рамка» (`B`): выберите класс в правой панели или клавишами `1`-`9`, затем протяните рамку по изображению. Инструмент «Выбор» (`V`) перемещает, изменяет размер, меняет класс и удаляет рамки; `Ctrl+Z` / `Ctrl+Shift+Z` — отмена и возврат.
- **Изменения сохраняются автоматически.** В верхней панели появляется «Сохранено», когда всё записано на сервер. `Ctrl+S` сохраняет немедленно, а несохранённое изменение никогда не пропадает молча: если сохранение не удалось, перед уходом с изображения вас спросят, а сохранение, конфликтующее с другой вкладкой или окном, останавливает правку, пока вы не перезагрузите изображение.
- **Горячие клавиши:** нажмите `?` (или кнопку `?` в верхней панели), чтобы открыть полный список. Они работают в любой раскладке, включая русскую.
- **Статусы изображений:** *unannotated* (нет рамок), *annotated* (есть хотя бы одна рамка или отмечено как фон), *reviewed* (вы отметили его проверенным) и *background*. Только изображения, которые вы явно отметили как **фон** (`G`), считаются «без объектов» при обучении; неразмеченное изображение — **не** фон, и последующий экспорт для обучения не будет считать его фоном.
- На одном изображении может быть не более 2000 рамок.
- Если редактор сообщает о **несовпадении ориентации** изображения, ваш браузер показывает его повёрнутым иначе, чем оно было сохранено (например, WebP с поворотом EXIF), поэтому рамки легли бы не туда, и это изображение нельзя размечать в этом браузере.

## Обучение модели

### Назначение выборок

Каждое изображение относится к одной выборке: **Train**, **Valid**, **Test** или ни к одной. Для обучения нужны размеченные изображения и в Train, и в Valid.

- **Вручную:** выделите изображения в сетке «Images» и используйте **Set split** («Назначить выборку»), либо измените выборку одного изображения через меню в верхней панели редактора (это не затрагивает индикатор сохранения и статус изображения).
- **Автоматически:** **Split dataset** («Разбить набор данных») показывает предпросмотр пропорций и просит подтверждение, прежде чем что-либо назначить.
- Для обучения используются только изображения, у которых есть хотя бы одна рамка или которые явно отмечены как фон. Неразмеченные изображения не берутся, даже если у них есть выборка, и изображения без выборки тоже не берутся.

### Запуск обучения

Откройте раздел **Training** («Обучение») проекта и нажмите **New training** («Новое обучение»). Значения по умолчанию: базовая модель `yolo26n` (`yolo26n-seg` для проекта `segment`), 100 эпох, размер изображения 640, размер батча **Auto** (16 на CPU) и устройство **Automatic** («Автоматически»). Базовой может быть и модель, которую вы раньше обучили в этом сервисе, вместо официальной. Кнопка **Start training** («Начать обучение») остаётся недоступной, а причины показываются на экране, пока в Train и Valid нет размеченных изображений.

- **Одновременно идёт один запуск.** Остальные ждут в очереди по порядку, и пока они в очереди, их можно удалить.
- **Закрытие браузера не влияет на запуск.** Откройте страницу запуска снова, чтобы увидеть прогресс.
- **Перезапуски:** перезапуск воркера (или всего стека) помечает идущий запуск как **interrupted** (прерван) и сохраняет запуски в очереди. Перезапуск только `api` идущий запуск не прерывает. Прерванный запуск можно возобновить, см. [Отмена и возобновление запуска](#отмена-и-возобновление-запуска).
- **При первом использовании официальная модель скачивается** в `data/weights/`. На хосте без доступа в интернет положите файл туда заранее сами, например `data/weights/yolo26n.pt`.
- **Обучение на CPU идёт медленно.** Для первой пробы возьмите маленькую модель, мало эпох и небольшой размер изображения.
- Аналитика использования Ultralytics при запусках обучения отключена.

### Наблюдение за запуском

Откройте запуск в списке **Training** («Обучение»), чтобы следить за ним. Страница обновляется сама, обновлять её вручную не нужно.

- **Три графика в реальном времени** растут после каждой эпохи: loss (сумма всех компонентов потерь, при наведении видна разбивка), mAP (mAP50 и mAP50-95, лучшая эпоха отмечена) и precision вместе с recall. Кривые обучения (Train) и валидации (Validation) нарисованы отдельно.
- **Строка статуса** показывает эпоху («Эпоха 7 из 100»), **полосу батчей**, которая движется внутри эпохи («Батч 3 из 12»), время обучения и оценку **оставшегося времени** («Осталось: ~…»). Пока оценить оставшееся время нельзя, там стоит «—».
- **После последней эпохи** в строке статуса стоит «Итоговая валидация…», пока лучшая контрольная точка проверяется на валидационных изображениях и модель регистрируется. Никогда не «Эпоха 101 из 100». Когда всё готово, карточка **«Итоговые результаты (best.pt)»** показывает precision, recall, mAP50 и mAP50-95 с вердиктом.
- **Перезагрузка страницы сохраняет историю.** Полная история графиков возвращается из `progress.jsonl` запуска и затем продолжается в реальном времени. Если живое соединение оборвалось, страница показывает «Переподключение…», а если восстановить его не удаётся, оставляет графики до последнего обновления.
- **Графики остаются у прошлых запусков.** Завершённый, упавший, отменённый или прерванный запуск показывает графики, которые успел построить, поэтому запуски можно сравнивать.

### Отмена и возобновление запуска

- **Отмена мгновенная.** Она доступна только на странице запуска, с подтверждением, где названа эпоха. Страница показывает «Отменяется…», и запуск становится **cancelled** (отменён) за несколько секунд; следующий запуск из очереди стартует сразу после. Эпоха, которая шла в момент отмены, теряется, все завершённые эпохи сохраняются. В Docker и на Linux воркер отправляет `SIGTERM` всей группе процессов обучения и `SIGKILL` через 10 секунд, если процесс ещё жив.
- **Возобновление продолжает тот же запуск.** Сохраняются сам запуск, его настройки (устройство, размер батча, размер изображения), его папка и графики; обучение продолжается с последней сохранённой эпохи, а запуск встаёт в **конец очереди**. На графиках появляется отметка «Возобновлено», в `progress.jsonl` запуска добавляется второе событие `train_start` с `"resumed": true`, а «Возобновлений» на странице запуска считает возобновления. Чтобы изменить любую настройку, начните новый запуск.
- **Возобновление доступно для каждого прерванного, отменённого или упавшего запуска, чья контрольная точка (`out/train/weights/last.pt`) ещё лежит на диске.** Это относится и к запускам, сделанным до этого обновления.
- **Возобновление отключено, а причина показана текстом на странице запуска, ровно в трёх случаях:** контрольная точка ещё не сохранена (`no_checkpoint`; начните новый запуск), все эпохи уже пройдены (`finished`; возобновлять нечего) или воркер уже отклонил контрольную точку этого запуска, потому что она отсутствует, повреждена либо обучение уже завершилось (`not_resumable`; это показывается как собственная подсказка ошибки после неудачной попытки возобновления, вместо этого начните новый запуск).
- **Возобновление из очереди можно отменить** кнопкой **«Отменить возобновление»** без потери прогресса: запуск возвращается в состояние cancelled и сохраняет контрольную точку и графики.
- **Автоматического возобновления нет.** После перезапуска прерванный запуск остаётся прерванным, пока вы не нажмёте **«Возобновить обучение»**.
- **Ограничение нативного Windows.** Когда воркер запущен нативно в Windows (не в Docker), отмена — это резкая жёсткая остановка (`TerminateProcess`), а не мягкий `SIGTERM`. При числе DataLoader-воркеров больше 0 (путь с GPU) дочерние процессы воркера могут остаться и их нужно завершить вручную в диспетчере задач. Освобождение памяти GPU после отмены проверяется в Фазе 12 на оборудовании NVIDIA.

### Когда запуск завершился ошибкой

Упавший запуск показывает заголовок, подсказку со следующим шагом, **исходное сообщение и журнал — всегда**. Заголовок и подсказка берутся по одному из этих кодов; всё нераспознанное показывается как `unknown`.

| Код | Заголовок | Что делать |
|---|---|---|
| `out_of_memory` | Не хватило памяти | Начните новый запуск с меньшим размером батча или изображения либо выберите модель поменьше. |
| `disk_full` | Закончилось место на диске | Освободите место в папке данных (`DATA_DIR`), затем возобновите запуск или начните новый. |
| `invalid_dataset` | Некорректный набор данных | Проверьте изображения и разметку, затем начните новый запуск. |
| `weights_download` | Не удалось загрузить веса модели | Проверьте подключение воркера к интернету или положите файл весов в `DATA_DIR/weights/`, затем начните новый запуск. |
| `process_killed` | Процесс обучения был принудительно остановлен | Система остановила процесс, чаще всего из-за нехватки памяти. Выделите Docker больше памяти или уменьшите размер батча или изображения, затем возобновите запуск или начните новый. |
| `not_resumable` | Невозможно возобновить | Сохранённая контрольная точка отсутствует, повреждена, либо обучение уже завершилось. Вместо этого начните новый запуск. |
| `unknown` | Непредвиденная ошибка | Подробности смотрите в журнале на странице запуска. Если ошибка повторяется, начните новый запуск. |

### История запусков

Список **Training** — это история всех запусков проекта: длительность, эпохи, ключевые настройки, итоговая (а для незавершённых запусков — по последней эпохе) mAP, размер набора данных и скачивание модели.

- **Сортировка и фильтр.** Нажмите на заголовок столбца, чтобы отсортировать по нему (повторное нажатие меняет направление), и используйте фильтр по статусу, чтобы показать, например, только упавшие запуски. Сортировка и фильтр хранятся в адресе страницы, поэтому перезагрузка или закладка их сохраняют.
- **Удаление завершённого запуска** (completed, failed, interrupted или cancelled) кнопкой **«Удалить запуск»**. После подтверждения, где названа модель, удаляются его папка (снимок набора данных, контрольные точки, графики, журналы) **и его модель**. Это нельзя отменить. Запуск, который ещё готовится или обучается, сначала нужно отменить, а запуск, чья модель — **база активного запуска**, нельзя удалить, пока тот не завершится. Запуск, который только ждёт в очереди, убирается кнопкой **«Убрать из очереди»**.
- **Промежуточный `best.pt`.** Упавший, прерванный или отменённый запуск предлагает **«Скачать промежуточный best.pt»**: лучшую эпоху из сохранённых на данный момент. Он **неполный** и никогда не попадает в ваши модели и не предлагается как базовая модель; модель создаёт только завершённый запуск.

### Скачивание модели

Когда запуск завершён, скачайте модель со страницы запуска или из списка запусков под именем `<project>_<run>_best.pt`. Загружайте её так же, как следующий в цепочке проект загружает `trained_models/best.pt`:

```python
from ultralytics import YOLO

YOLO("plates_run-3_best.pt").predict("image.jpg")
```

Проверить скачанный файл можно той же простой загрузкой `YOLO(path)` и одним предсказанием:
```bash
uv run python scripts/verify_model_download.py plates_run-3_best.pt --image image.jpg
```
Скрипт печатает задачу и имена классов модели и завершается строкой `OK`. Без `--image` предсказание выполняется на пустом кадре.

- Проекту, который использует модель, нужна версия Ultralytics, поддерживающая семейство базовой модели. Файл записывает версию Ultralytics, которой он обучен (8.4.159); для YOLO26 нужен Ultralytics 8.4 или новее.
- Файл `.pt` содержит во внутренних аргументах обучения внутренние пути к файлам сервера (расположение набора данных, проекта и модели). Для загрузки это безвредно и носит лишь информационный характер.
- Файл `.pt` — это pickle и может выполнять код при загрузке — см. [уведомление о безопасности](#уведомление-о-безопасности--прочитайте-перед-запуском).

## Конфигурация

Все переменные читаются из файла `.env` в корне репозитория (см. `.env.example`). Ни одна не обязательна — у каждой есть безопасное значение по умолчанию.

| Переменная | По умолчанию | Значение |
|---|---|---|
| `DATA_DIR` | `./data` | Каталог на хосте, смонтированный (bind mount) в контейнеры для всех данных приложения. |
| `BIND_ADDR` | `127.0.0.1` | Сетевой интерфейс, на котором сервис `web` публикует свой порт. `0.0.0.0` открывает его для всей вашей локальной сети — см. уведомление о безопасности выше. |
| `PORT` | `8080` | Порт на хосте, по которому доступно приложение. |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | Список Host-заголовков через запятую, которые принимает API (или `*` для любых). Добавьте сюда адрес/имя хоста вашей локальной сети, если вы установили `BIND_ADDR=0.0.0.0`. |
| `SQLITE_JOURNAL_MODE` | `WAL` | Режим журналирования SQLite. См. [Устранение неполадок](#устранение-неполадок), когда стоит изменить это на `DELETE`. |
| `MAX_UPLOAD_MB` | `50` | Максимальный размер одного загружаемого изображения в МБ. Относится только к маршруту загрузки изображений; все остальные маршруты API сохраняют лимит запроса 1 МиБ. |

## Настройка окружения разработчика

Это нужно для запуска бэкенда и фронтенда нативно (не в Docker) для разработки или запуска набора тестов.

1. **Установите [uv](https://docs.astral.sh/uv/getting-started/installation/)** (менеджер пакетов/проектов Python):
   - Windows (PowerShell): `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`
   - macOS/Linux: `curl -LsSf https://astral.sh/uv/install.sh | sh`

   Системный `python` у вас может быть другой версии (например, Python 3.14) — это нормально. `uv` читает `.python-version` (в этом репозитории закреплена версия `3.12`) и автоматически устанавливает и использует именно эту версию Python. **Всегда запускайте команды Python через `uv run`**, а не через `python`, который стоит в `PATH`.

2. **Установите зависимости бэкенда** (из корня репозитория):
   ```bash
   uv sync --locked
   ```
   Это установит сервис FastAPI, PyTorch 2.14.0 (CPU) и Ultralytics 8.4.159 для воркера, а также инструменты разработки (pytest, ruff).

3. **Установите Node.js 24 LTS + npm** (если ещё не установлены), затем установите зависимости фронтенда:
   ```bash
   npm --prefix frontend ci
   ```

### Наполнение большого проекта и проверка плавности сетки

Сетка на странице «Изображения» виртуализирована, поэтому должна оставаться плавной при тысячах изображений. Чтобы это проверить, заполните проект сгенерированными изображениями через настоящий API загрузки (стек должен быть запущен, например `docker compose up --build`):
```bash
uv run python scripts/seed_images.py --count 5000                       # создаёт (или переиспользует) проект "seed-5000"
uv run python scripts/seed_images.py --count 5000 --project-id 3        # наполнить существующий проект
uv run python scripts/seed_images.py --count 5000 --base-url http://127.0.0.1:8080
```
Скрипт загружает пачками по 20 изображений в 4 параллельных потока (`--batch-size`, `--workers`) и печатает `project=<id> added=<n> duplicate=<n> rejected=<n> elapsed=<s>s`. Изображения детерминированы по индексу (и `--seed`), поэтому повторный запуск с теми же аргументами сообщит обо всех изображениях как о дубликатах. 5000 изображений занимают около 40 МБ на диске и примерно минуту.

Ручная проверка плавности: откройте страницу **Изображения** проекта, прокрутите её сверху вниз и выполните в консоли DevTools браузера `document.querySelectorAll("img").length`. Прокрутка должна оставаться плавной, а число элементов — держаться в пределах нескольких сотен, а не тысяч.

## Устаревшие CLI-скрипты

Оригинальные скрипты обучения из командной строки по-прежнему работают, поведение не изменилось, запускаются из корня репозитория:
```bash
uv run python train_yolo.py
uv run python finetune_yolo.py
```
Оба настраиваются через `config/config.ini` и пишут результат в `runs/` (обе директории в .gitignore). Их общие вспомогательные функции (выбор устройства, оценка качества) теперь находятся в `backend/src/yolo_trainer_common` и импортируются обоими скриптами.

Известные ограничения:
- `gpu_test.py` требует GPU NVIDIA и завершится с ошибкой на машинах только с CPU. В одной из следующих фаз (Фаза 12) он будет заменён страницей диагностики внутри приложения.
- `train_yolo.py` читает конфигурацию из `Config/Config.ini` (с заглавной `C`), что работает только на файловых системах, нечувствительных к регистру (Windows и macOS по умолчанию). На файловых системах, чувствительных к регистру (большинство настроек Linux), этот путь не будет найден — в этом случае используйте `config/config.ini`.

## Устранение неполадок

**Ошибка SQLite: "database disk image is malformed"** — Это известный риск Docker Desktop (Windows/macOS): режим WAL в SQLite полагается на согласованность разделяемой памяти, которую мост bind-mount между виртуальными машинами в Docker Desktop не гарантирует полностью под нагрузкой записи. Нативные хосты Docker на Linux этому не подвержены (bind mount там — реальная файловая система хоста, без границы виртуальной машины).
1. Остановите стек: `docker compose down`
2. При необходимости восстановите `./data` из резервной копии
3. Добавьте `SQLITE_JOURNAL_MODE=DELETE` в `.env` (жертвует частью пропускной способности при параллельном чтении, но убирает зависимость от согласованности WAL между виртуальными машинами)
4. Перезапустите: `docker compose up`

`SQLITE_JOURNAL_MODE` в `.env` действует и для `api`, и для `worker`, поэтому оба всегда работают в одном режиме. На хостах macOS, если база данных сообщает о повреждении, установите `DELETE`.

**"The training worker is not responding" («Воркер обучения не отвечает»)** — Запуск стоит в очереди, но его никто не берёт. Проверьте, что воркер работает, командой `docker compose ps`, затем посмотрите его вывод через `docker compose logs worker`. Перезапуск `docker compose restart worker` безопасен: запуски в очереди сохраняются.

**Запуск завершился ошибкой "Could not download …"** — Воркер не смог скачать официальные базовые веса. Либо дайте хосту доступ в интернет, либо положите файл в `data/weights/` сами (например, `data/weights/yolo26n.pt`) и запустите обучение снова.

**Порт 8080 уже занят** — Установите другой `PORT` в `.env` и перезапустите.

**"Invalid host header" (HTTP 400)** — Добавьте хост/IP, с которого вы подключаетесь, в `ALLOWED_HOSTS` в `.env`.
