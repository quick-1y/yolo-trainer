## Phase Goal

ROADMAP goal (verbatim): "A user can annotate images one by one with bounding boxes in a fast, keyboard-driven editor without ever losing work". This plan delivers delete, undo/redo (success criterion 3) and the keyboard layer every later slice adds its keys to (success criterion 4).

<objective>
A user deletes boxes, undoes and redoes any edit from the tool bar or the keyboard, and drives tools from the keyboard on any keyboard layout. One shortcut table becomes the single source for key handling and, in Plan 03-13, for the on-screen reference.

Purpose: undo/redo is the safety net behind "never losing work"; the physical-key table prevents the Russian-layout breakage RESEARCH verified (Pitfall 8).
Output: `deleteBox`, Undo/Redo buttons, `lib/shortcuts.ts`, `useEditorHotkeys`, Esc draft cancel, tests.
</objective>

Mantine `useHotkeys` facts, read from frontend/node_modules/@mantine/hooks/esm/use-hotkeys/{use-hotkeys,parse-hotkey}.mjs (version 9.6.3): it binds `keydown` on `document.documentElement`; items are `[hotkey, handler, { preventDefault = true, usePhysicalKeys = false }]`; events whose target is INPUT, TEXTAREA or SELECT (or contentEditable) are ignored; `parseHotkey` LOWER-CASES the whole hotkey string before `normalizeKey` strips a case-sensitive "Key" prefix, so a hotkey written as "KeyV" becomes "keyv" and never matches. With `usePhysicalKeys: true` write letters as lowercase letters ("v", "mod+z"), digits as "digit1".."digit9" / "digit0", and named keys as "Delete", "Backspace", "Escape", "ArrowLeft", "ArrowRight", "shift+slash"; they are compared with `event.code` (KeyV -> "v", Digit1 -> "digit1"), independent of the keyboard layout. Modifiers must match exactly ("mod" = Ctrl or Meta), so redo needs two entries. The handler list is read at event time, so passing `[]` disables everything.
