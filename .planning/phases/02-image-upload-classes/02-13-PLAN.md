<objective>
Close UAT gap G-02-5 (02-UAT.md test 5, 02-REVIEW.md CR-01 and WR-01): deleting a large selection must work for any selection size, and deleting every loaded image must lead to the next page instead of a false empty state.

- WR-01: useDeleteImages sends every selected id in one POST /images/delete, while the backend caps `ids` at 1000, so a selection of 1001+ images fails with a raw 422 in the dialog. The fix is in the client: split the ids into chunks of 1000, send them one after another, and sum `deleted`. The backend limit stays (D-11 delete with confirmation, D-19 rows first then files are unchanged).
- CR-01: after the user deletes every loaded image while the server still has more pages, ImagesPage renders EmptyState. The grid is unmounted, so VirtuosoGrid's endReached never fires (it also never fires for zero items), and pruneDeletedImages keeps `next_cursor`. Fix: an effect loads the next page while the loaded list is empty and a next page exists. EmptyState shows only when no next page exists (D-06 cursor-paged grid).

Purpose: the owner reproduced WR-01 (1067 selected images gave a 422) and approved fixing both defects now. The phase architecture is already proven (02-01 tracer, 02-11 selection and delete), so this plan adds two focused TDD tasks on that path. It does not add a new tracer.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser SPA -> API `POST /api/projects/{id}/images/delete` | Client-chosen id lists cross here. The server validates size (max 1000) and project scope. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-13-01 | Denial of service | POST /images/delete request size | low | mitigate | Backend limit ImageDeleteRequest.ids max_length=1000 stays unchanged (pinned by test_exactly_1000_ids_are_accepted and the 422 test). The client sends DELETE_BATCH_SIZE chunks strictly one at a time; the hook test asserts at most one request in flight. |
| T-02-13-02 | Tampering (integrity of displayed state) | useDeleteImages partial failure | medium | mitigate | On a failed chunk, the ids of the chunks that already succeeded are pruned from every cached image list and the project counts are invalidated before the error is rethrown. The hook test asserts the cache state after chunk 2 fails. |
| T-02-13-03 | Denial of service | ImagesPage empty-list next-page effect | medium | mitigate | The effect fires only when data is loaded, the list is empty, a next page exists, nothing is fetching and the last next-page load did not fail. Retry happens only via the footer button. The integration test asserts exact "c1" request counts (2, then 3 after one click). |
| T-02-13-04 | Elevation of privilege / Tampering | Retry after a partial failure resends already-deleted ids | low | accept | delete_images scopes rows to the project and ignores ids that no longer exist (a repeated request deletes nothing), so a retry cannot delete anything outside the user's own selection. The toast then reports only that attempt's count. |
| T-02-13-05 | Spoofing (CSRF) | POST /images/delete | low | accept | Unchanged by this plan. The route relies on the JSON Content-Type CORS preflight (decision 02-11). Hardening is tracked separately as 02-REVIEW WR-03 and is not part of G-02-5. |
